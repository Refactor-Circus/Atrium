# Atrium

This repository is a Laravel package. Keep the package focused, idiomatic, and easy for Laravel developers to install, test, and maintain.

## Package Conventions

- Use Laravel-native package APIs and the existing service provider shape before adding abstractions.
- Keep package names, namespaces, Composer metadata, publish tags, documentation, and examples aligned with `refactor-circus/atrium`.
- Add only the files and dependencies needed for the package behavior being implemented.
- Prefer explicit Laravel package code over helper abstractions unless the extension point is real.
- Keep tests focused on observable package behavior through public APIs, service provider wiring, commands, routes, published resources, and documentation promises.

## Architecture Conventions

These are recorded in full in the global standards and under `docs/agent/standards/`; the short form:

- **Code lives in domain modules.** `src/Domains/{Domain}/` (`Access`, `Dashboard`, `Frontend`, `Integrations`, `Navigation`, `Plugins`, `Screens`, `Search`, `Settings`, `Themes`, `Widgets`), namespace `RefactorCircus\Atrium\Domains\{Domain}`, each with a `{Domain}ServiceProvider` registered by `Domains\DomainServiceProvider`. Models are `{Entity}Model` in `Models/`; value objects in `Data/`; registries in `Services/`. Package-wide base classes, contracts and `Support/` stay at the top level. A moved model keeps its old class name as a morph alias. See `architecture/domain-modules` (global standard) and `docs/agent/standards/atrium/domains.md`.
- **Actions own mutating logic.** Extend `RefactorCircus\Keystone\Actions\Action`, implement a `protected handle()` with a concrete return type, and let callers use `execute()`. Action input is a `final readonly` `{Action}Data` in the domain's `Data/` (on `RefactorCircus\Keystone\Data\Data`), never an array: fields are promoted constructor properties (camelCase of the input keys; `T|Missing = new Missing` for partial updates), `rules()` lives on the Data, and the starting event carries it. Requests' `rules()` return `XData::rules()` and `persist()` builds with `XData::fromValidated($this->validated())` - never `XData::from()` in a request; untrusted input elsewhere uses `XData::from()`, which validates, and code that vouches for its values uses `new XData(...)`. Nested input is nested Data (`#[ListOf(WidgetPlacementData::class)]`), checked by the parent's rules under its key (`widgets.*.widget_key`). `tests/ArchTest.php` checks this with Keystone's `Testing\Arch`, along with the event pair on every action, writes only inside a transaction, and a `{Entity}{Hook}Event` for every model hook. `handle()` dispatches a starting `{Subject}{Verb-ing}ActionEvent` with the input, runs the work in a private `perform()` wrapped in `DB::transaction()`, then dispatches the finished `{Subject}{Verb-ed}ActionEvent` with the result.
- **Requests own validation, authorization, and the call into an action.** Extend `RefactorCircus\Atrium\Http\Requests\Request` and implement `persist()`. Controllers only `return $request->persist();` and never contain database calls.
- **Events are final classes using `Dispatchable` and `SerializesModels`.** Action events live in the domain's `Events/` and implement `RefactorCircus\Keystone\Contracts\ActionStartingEvent` or `ActionFinishedEvent` (after commit); every action has one of each. Model events live beside them, are named `{Entity}{Hook}Event`, implement `RefactorCircus\Keystone\Contracts\ModelLifecycleEvent`, and are mapped by the `RefactorCircus\Keystone\Models\Concerns\DispatchesModelEvents` trait every model uses.
- **Shared runtime lives in `refactor-circus/keystone`.** The `Action` and `Request` bases, event contracts, `DispatchesModelEvents`, the package registry and the audit seams come from Keystone, which every package in the suite requires. Atrium registers itself as the `atrium` package from `AtriumServiceProvider::definition()`.
- **Tables are configurable.** Models resolve their table with `getTable()` from `Support\Tables` (`atrium.tables`, on Keystone's `Database\Tables`), and the migrations use the same keys, never literal `atrium_*` names. `tests/ArchTest.php` checks with `Arch::literalTableNames()`, and that every model has a policy in `atrium.policies` with `Arch::modelsWithoutPolicies()`; `tests/Modes/RenamedTables` reruns dashboard flows with every table renamed.
- **Requests authorize through policies.** `authorize()` calls `$this->allows()` / `allowsEach()`: `viewAny`/`create` on the model class, `view`/`update`/`delete` on the instance. Every model has a policy; policies extend `Domains\Dashboard\Policies\Policy`, are registered from `atrium.policies` by `registerPolicies()`, and child-model policies defer to the dashboard through the Gate with Keystone's `Policy::allowsOn()`.
- **Atrium is a JSON API.** Each domain loads its own `routes.php` with `loadApiRoutesFrom()` into the one group from `atrium.routes.*` (prefix `atrium/api`, middleware `['web', 'auth', Authorize::class]`, the page's session, names `atrium.*`); plugin routes sit in it under `plugins/{key}`, named `atrium.plugins.{key}.*`. Nothing in `src/` renders HTML except the `Frontend` domain's one page, `atrium::app` (`resources/views/app.blade.php`), served at `atrium.client_path` with its files from the `atrium.assets` route: `tests/ArchTest.php` fails on `view(`, `Illuminate\View` or `Blade::` anywhere else. Atrium ships no authentication; the host's guard goes before `Authorize`, which stays last. Every payload is a `final` resource on Keystone's `JsonResource`: beside its model in `Domains/{Domain}/Resources/`, or in `Domains/{Domain}/Http/Resources/` with no model behind it; abilities go in `meta.abilities`. Bind by `{dashboard:slug}` and `{widget:uuid}`.
- **Screens declare themselves.** Every Atrium endpoint that serves a screen builds `Domains\Screens\Data\Screen::standard()` with its key, record and kind, resolves it with `ScreenExtensions::resolve()` after its own authorization, and sends it with `ResolvedScreenResource` beside its payload (Settings declares `atrium.settings` and `atrium.settings-panel`). Other packages add tabs and sections through `Atrium::screens()` from `boot()`. Atrium requires only Keystone and has no audit concept of its own.
- **Atrium hosts the suite's front ends** (Cortex, Guardian, Impex, Keen, PennantPlus, Polycart, Roster, Showroom), whose v2 ship only a JSON API and MCP. Roles and permissions live in Guardian, not Roster: the `guardian.roles`, `guardian.role`, `guardian.permissions` and `guardian.role-assignments` screens replace Roster's, and the `guardian.access` hook puts role assignments on Roster's organization and user screens. The framework is `src/Domains/Integrations/` (`IntegrationRegistry`, `IntegrationManifests`, `ManifestSchema`, `ManifestValues`, `IntegrationHooks`, the `InstalledPackages` seam, `IntegrationFeatures`, `ScreenDeclaration`, `atrium.screens.show`). Atrium knows no package (D-090): each declares its integration in a static JSON manifest, `integration.json` (its source `atrium/src/integration.json`, shipped in `dist/atrium/` and named by `extra.atrium.integration`), checked against `ui/sdk/schema/integration.schema.json` and the manifest rules: nav items, widgets, a settings panel, search source descriptors, screens with their front-end paths, `features` (Pennant names) and `hooks` (the tabs and sections it adds to other packages' screens, in the package whose API they call). Labels are plain English through `__()`; config-derived values are `$config` expressions limited to `{pkg}.*` and `atrium.integrations.{pkg}.*`. Never add a package's declaration, feature class or label file to Atrium (`src/Integrations/` and `lang/en/integrations/` are gone; `ManifestTest` checks); `tests/ArchTest.php` and `NoPackageCodeTest` fail on any `RefactorCircus\{Cortex,Guardian,Impex,Keen,PennantPlus,Polycart,Roster,Showroom}` in `src/`. An integration registers when Atrium finds its manifest (an installed package's through `atrium:discover`, an `Atrium::module()` folder's, or `Atrium::integration()`), `atrium.integrations.{pkg}.enabled` is true and it has an API base; it is active per user while its `features` resolve through Pennant (all on without it). See the local standard `atrium/integrations` (`docs/agent/standards/atrium/integrations.md`).
- Do not require a feature-flag package such as Pennant; gating is the host application's concern. Pennant is a dev dependency only, for `Domains\Themes\Features\ThemeSwitcherFeature`, which only Pennant resolves, and for the integration flag tests; `IntegrationFeatures` asks Pennant only when it is available, behind a seam. Feature-flag management is `refactor-circus/pennantplus`'s API, rendered by the PennantPlus integration's `/pennantplus/features` page.

## PHP Conventions

- The package targets PHP 8.5. Use its syntax where it earns its place.
- Value objects (`NavItem`, `WidgetDefinition`, `SettingsPanel`, `SearchSource`, `SearchResult`, `Theme`) expose state as `public private(set)` properties rather than getter methods, so they read as `$item->label` and stay immutable from the outside. Configure them through the fluent setters, which share the property's name.
- Closures and other internals stay `private`; only meaningful state is publicly readable.

## Frontend Conventions

- **Atrium ships its front end prebuilt** (D-079): one Blade page, `atrium::app`, at every path under `atrium.client_path` (default `/atrium`, behind `atrium.client.middleware`), loads Atrium's Vue 3 + Vite app from the committed `dist/` and every module's script and stylesheet, through the `/vendor/atrium/{owner}/{version}/{path}` route (`atrium.assets.path`; no publish step, D-081). Hosts run no Node. Sources are the pnpm workspace in `ui/`: `ui/sdk` (`@refactor-circus/atrium`, the SDK: registry, `useAtrium*` composables, `Atrium*` components, stores, types, `defineAtriumModule()`, the Vite preset, test helpers), `ui/app` (Atrium's entry, router, layouts and core pages) and `ui/workbench` (the workbench's module). The suite packages' modules live in the packages (D-089). Vue 3, Vue Router, Pinia, Nuxt UI 4 (its Vite plugin in Vue mode), vue-i18n and VueUse. Node and pnpm are pinned in `.nvmrc` and `ui/package.json`; `ui/pnpm-lock.yaml` is committed.
- **Modules own their front end** (D-082, `MODULES.md`). A module's entry calls `defineAtriumModule({ key, routes, widgets, extensions, settingsPanels, liveResolvers, searchSources, responseHandlers, screens, messages, setup })`; a package declares it in `composer.json` under `extra.atrium` (`scripts`, `styles`, and `integration`, its manifest, D-090), discovered by `atrium:discover`, with no Composer dependency on Atrium; an app adds its own with `Atrium::module()`, `Atrium::script()`, `Atrium::style()` or `atrium.scripts` / `atrium.styles`. The import map's shared modules (`ATRIUM_SHARED_API`, `ui/sdk/vite/shared.mjs`) are a versioned API: removing a specifier or a library's new major is a new major. Modules build with `atriumModule()` from `@refactor-circus/atrium/vite` (which checks `src/integration.json` and copies it to `dist/atrium/integration.json`) and commit `dist/atrium/` with its `build.json`; their Vitest suites check the manifest with `expectIntegrationManifest()` from `@refactor-circus/atrium/testing`. The schema (`ui/sdk/schema/integration.schema.json`) is read by both PHP (`ManifestSchema`) and the SDK (`ui/sdk/vite/manifest.mjs`); change both, and `ui/sdk/test/fixtures/manifests/cases.json`, together.
- **PHP sends data, Vue renders it.** Widgets, screen tabs and sections and settings panels are sent as `{key, component, data}`; `component` defaults to the definition key. The front end renders the component a module registered under it (`widgets`, `extensions`, `settingsPanels`, or `useAtrium().widget()` / `.extension()` / `.settingsPanel()`), and a fallback card for an unregistered key. Resolver output goes through `Support\JsonData` (JSON-serializable only; failures isolated to `data: null` plus `error` outside `local` and `testing`). Links are `{path, external}` from `Support\ClientPath` against `atrium.client_path`.
- Icons are Iconify names (`i-lucide-home`), checked by `Support\Iconify` in every `icon()` setter. The front end bundles `lucide` and never calls the Iconify API unless `atrium.icons.remote` is on; a module adds packs with `addAtriumIcons()`.
- Styling uses Nuxt UI and the design tokens in `ui/sdk/css/theme.css`, shared by Atrium's stylesheet (`ui/app/src/assets/atrium.css`) and every module's (`@refactor-circus/atrium/module.css`). Nuxt UI is compiled once, in Atrium's build, with the theme config in `ui/sdk/vite/ui-config.mjs`; modules never run or bundle it. Themes (`Domains\Themes`) are sent in the shell as token values, light and `-dark` together, and applied on `:root`; never hard-code a colour a theme should own. `config('atrium.theme')` retunes the built-in `atrium` theme.
- Atrium's own strings live in `ui/sdk/locales` (`en` only ships); each module brings its own `messages`; server-side labels are translated by Laravel.
- The API and the front end share one contract: PHP feature tests compare payloads with `ui/sdk/test/fixtures/*.json` and rewrite them only with `UPDATE_FIXTURES=1`; Vitest checks the fixtures against `ui/sdk/src/types/atrium.ts`. `Atrium::API_VERSION` must match the major.minor of `ui/sdk/package.json`. `BuildFreshnessTest` fails when a committed build's source hash is stale (D-085).
- Test hooks use `data-testid` attributes, which the Vitest suites in `ui/sdk/test` and `ui/app` (and each package's `atrium/test`) select.
- **Suite integrations' modules live in their packages** (D-089): each of Cortex, Guardian, Impex, Keen, PennantPlus, Polycart, Roster and Showroom keeps its module in its own `atrium/` (`src/atrium.ts` with `defineAtriumModule`, its `screens` map and the `// Not ported (D-032)` list; `src/routes.ts` with explicit routes keeping the old names, such as `impex-runs-run`; cross-package hooks in the module of the package whose API they call), commits `dist/atrium/` and declares it in `extra.atrium`; `MODULES.md` is the guide to writing one, with those eight as examples. Atrium stages no module and vendors no package client: never add `ui/modules/` or copy a package's `openapi.json` or `schema.d.ts` into Atrium. Vue calls each package's API only through `useAtriumIntegration(pkg).client` (`openapi-fetch`, typed by the module's `AtriumIntegrationPaths` augmentation over the package's own generated client, signed like every Atrium request) and `atrium.screens.show`. Atrium's own `openapi.json` comes from `composer openapi:export` and `ui/sdk/src/client/schema.d.ts` from `pnpm -C ui generate:client`; `OpenApiTest` fails when either is stale. Each package also ships its integration manifest (D-090); Atrium's tests read fixture copies in `tests/Fixtures/Manifests/{pkg}/`, and the integration fixtures (`ui/sdk/test/fixtures/integrations/*.json`) stay Atrium's contract.
- **Response handlers and shell-less pages.** A module's `responseHandlers` (or `useAtrium().responseHandler(key, handler)`) sees every response of every integration client, `useAtriumClient()` and `useAtriumApi()`, in registration order, before the caller; Guardian's (`guardian.two-factor`) sends a 403 `two_factor_challenge_required` / `two_factor_enrollment_required` to `/guardian/two-factor/challenge` or `/setup`, and `useAtrium().notify()` shows its deadline notice. Pages that must work without a shell (`/roster/invitations/:token`, the two Guardian two-factor pages) declare `meta: { atrium: { public: true } }` on their route, render in the public layout, build their own client and never call `atrium.screens.show`.
- **Atrium* components compose Nuxt UI; no bespoke markup for things Nuxt UI provides** (D-091). The shell is Nuxt UI's dashboard (`UDashboardGroup`, `UDashboardSidebar`, `UDashboardNavbar`, `UDashboardSearch`, `UDashboardToolbar`), the deck's look lives in `ui/sdk/vite/ui-config.mjs` as slot classes over the `--atrium-*` tokens, and `atrium.css` keeps only tokens, fonts, the base layer and the plain-HTML styling modules' pages rely on. `ui/sdk/test/nuxt-ui-guard.test.ts` fails on a raw `<button>`, `<input>`, `<select>`, `<textarea>`, `<table>`, `<details>` or `<a href>` (outside `AtriumLink`) in an SDK or app component.
- **The SDK owns every shared component and style.** Modules ship no design tokens of their own; their Vue components build on Nuxt UI (`@refactor-circus/atrium/ui`) and the SDK's `Atrium*` components. When a package needs new generic UI, add an `Atrium*` component to `ui/sdk`. See `docs/agent/standards/atrium/components.md`.

## Quick Commands

- Full validation (PHP): `composer test`
- Front-end gate: `composer test:ui` (frozen pnpm install, the generated-client and theme checks, typecheck, Vitest, every build). Work is done only when it passes too, whenever anything under `ui/` or the API's payloads changed; commit the rebuilt `dist/` and `ui/workbench/dist/atrium/`.
- Formatting check: `composer lint:check`
- Static analysis: `composer analyse`
- Pest tests: `composer test:unit`
- Contract fixtures: `UPDATE_FIXTURES=1 vendor/bin/pest`
- Front end: `pnpm -C ui build`, `pnpm -C ui test`, `pnpm -C ui typecheck`, `pnpm -C ui dev` (rebuild on change), `pnpm -C ui theme:check`
- Atrium's OpenAPI and SDK client: `composer openapi:export`, then `pnpm -C ui generate:client`
- Workbench build: `composer build`
- Workbench server: `composer serve`, then open http://127.0.0.1:8000/atrium (signed in through `/_workbench` as admin@example.com; the suite APIs are stood in by `workbench/app/Atrium/SuiteStandIn.php` at `/_suite/{pkg}`; the integrations are declared by `tests/Fixtures/Manifests/{pkg}/integration.json`, or a checkout's own manifest; set `ATRIUM_SUITE_PATH` to a folder of sibling package checkouts to load their built modules and stand in for their APIs from their `openapi.json`, otherwise the integrations show fallback cards)
